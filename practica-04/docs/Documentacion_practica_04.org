** Pruebas Unitarias

Una *Prueba Unitaria* verifica un comportamiento pequeño del sistema: una función, un método o una regla concreta. Para el desarrollo de las mismas se recomienda seguir el siguiente flujo:

#+BEGIN_EXPORT latex

\begin{figure}[H]

\centering

{\large
\textbf{Problema}
\,$\longrightarrow$\,
\textbf{Modelo}
\,$\longrightarrow$\,
\textbf{Casos}
\,$\longrightarrow$\,
\textbf{Pruebas}
\,$\longleftrightarrow$\,
\textbf{Implementación}
}

\caption{Flujo general del diseño de pruebas.}

\end{figure}

#+END_EXPORT

*Nota:* El resultado esperado se decide antes de ejecutar el código. No se copia lo que devuelve la implementación.

Los casos de prueba definidos se clasifican como:

- *Normal:* Un valor dentro de la regla.
- *Frontera:* Justo antes, en y después de un límite.
- *Inválido:* Un valor que el sistema debe rechazar.
- *Excepción:* Un error esperado.
- *Cruce de reglas:* Cuando dos condiciones se cumplen al mismo tiempo.

*Ejemplo:*

Si hasta 15 minutos es gratis, y desde 16 se cobra, probar 14, 15, 16 y 17.


#+BEGIN_EXPORT latex
\Needspace{6\baselineskip}
#+END_EXPORT

** Estructura de una prueba Arrange - Act - Assert

- *Arrange:* Preparación de los datos, objetos, o estado inicial.
- *Act*: Ejecución de la función o método que se desea probar.
- *Assert:* Comprobación de que lo obtenido sea lo esperado.

*Ejemplo:*

#+BEGIN_EXPORT latex

\begin{lstlisting}[style=practica]
# Arrange
minutos = 16

# Act
resultado = sistema.calcular_total(minutos, "normal", False)

# Assert
assert resultado == 20.0
\end{lstlisting}

#+END_EXPORT

*Nota:* Una buena prueba responde tres preguntas: *¿qué regla comprueba?, ¿qué entrada utiliza? y ¿qué resultado debería producir?*


#+BEGIN_EXPORT latex
\Needspace{7\baselineskip}
#+END_EXPORT

* Objetivo

El alumno diseñará un conjunto de pruebas unitarias para verificar el comportamiento de un sistema a partir de su especificación, no únicamente a partir de lo que hace el código.

Al finalizar la práctica, el alumno deberá ser capaz de:

- identificar casos normales;
- identificar casos frontera;
- detectar entradas inválidas;
- verificar errores y excepciones;
- escribir pruebas usando el patrón Arrange–Act–Assert;
- justificar de qué regla del modelo proviene cada caso de prueba;
- ejecutar una suite de pruebas y analizar sus resultados;
- diferenciar entre “la prueba pasó” y “el programa es correcto”.


#+BEGIN_EXPORT latex
\Needspace{7\baselineskip}
#+END_EXPORT

* Desarrollo de la práctica


#+BEGIN_EXPORT latex
\Needspace{6\baselineskip}
#+END_EXPORT

** Durante la práctica

1. Lea primero el modelo.
2. Diseñe los casos sin ejecutar todavía el sistema.
3. Escriba el resultado esperado de cada caso.
4. Implemente las pruebas.
5. Ejecute la suite.
6. Si alguna prueba falla, no cambie inmediatamente la prueba.
7. Compare:
   
#+BEGIN_CENTER

*modelo esperado* vs. *resultado obtenido*

#+END_CENTER

8. Determine si el problema está en:
   1. la implementación;
   2. la prueba;
   3. la interpretación del modelo.

#+END_EXPORT

*** Modelo del Sistema: Ticket de Estacionamiento

Comportamiento esperado:

*R1.* Los minutos deben ser un número entero mayor o igual que 0.

*R2.* Los tipos de clientes válidos son:

- *"normal"*
- *"frecuente"*

*R3.* Si el boleto está perdido, el costo final es de @@latex:\$@@300.00, sin importar los minutos ni el tipo de cliente.

*R4.* Si los minutos son 0, el costo es @@latex:\$@@0.00

*R5.* De 1 a 15 minutos, el costo es @@latex:\$@@0.00

*R6.* De 16 a 60 minutos, el costo es de @@latex:\$@@20.00

*R7.* Después de 60 minutos se cobran @@latex:\$@@20.00 por la primera hora y @@latex:\$@@15.00 por cada hora adicional *iniciada*.

*R8.* Un cliente *"frecuente"* recibe un 10% de descuento sobre el costo calculado, excepto cuando perdió el boleto.

*R9.* El costo nunca puede ser negativo.

*R10.* Si los minutos son negativos, el sistema debe lanzar un error.

*R11.* Si el tipo de cliente no es válido, el sistema debe lanzar un error.
